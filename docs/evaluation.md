# Оценка качества

## Цель

Evaluation отвечает на узкий вопрос: может ли конкретная ревизия LocalScript в зафиксированном окружении вернуть проверенный результат для заявленного набора задач, не выдавая невалидный код за успех. Она не измеряет универсальную способность модели писать Lua.

## Корпусы

| Набор | Размер | Роль | Публикация |
|---|---:|---|---|
| Live v1 | 6 сценариев | единственный живой корпус разработки и релиза | в репозитории |
| Synthetic blind holdout v2 | 8 кейсов, из них 2 по безопасности | однократная проверка замороженного кандидата | только хеш и агрегаты |

Живой корпус покрывает шесть разных форм задачи: скалярное преобразование, фильтрацию с проекцией, агрегацию, вложенный объект, JSON-конверт и уточнение. Шесть сценариев — это не «мало кейсов ради скорости», а отказ от корпуса, который проверял одно и то же в двенадцати вариантах: старые 140 регрессионных кейсов опирались на семейства задач и канонические формы ответа, которых в typed workflow больше нет.

Безопасность проверяется детерминированными тестами AST-политики и ограниченного runtime, без единого обращения к модели. Держать её в живом корпусе значило бы тратить GPU на то, что и так проверяется за миллисекунды и строже.

`holdout-v2` заморожен 13 августа 2026 года отдельным Codex-контекстом, который получил только публичную продуктовую спецификацию и не видел ни кода, ни старых evals. В Git попадают его SHA-256, число кейсов и категории; сам файл лежит вне репозитория. Набор честно называется `synthetic blind`, а не независимым внешним benchmark: его составлял агент по нашей же спецификации.

Предшественник `holdout-v1` помечен как неиспользованный и заменённый: он составлялся под снятую family-архитектуру и ни разу не участвовал в релизном прогоне.

## Что проверяет один кейс

Кейс с ожидаемым исходом `completed` считается пройденным, если workflow опубликовал код, диагностик нет, а выполнение кода в ограниченном runtime дало ровно ожидаемый JSON. Кейс, который обязан завершиться отказом, проверяется зеркально: совпал статус, и код **не** опубликован. Reference code в prompt не передаётся ни в одном корпусе.

## Метрики

- `verified_completion_rate` — доля кейсов с исходом `completed` и пройденным оракулом;
- `invalid_success_count` — результаты, объявленные успешными вопреки проваленной проверке; обязательное значение — ноль;
- `revision_count` и `revision_rescue_rate` — как часто нужна была правка и как часто она спасала кейс;
- `stage_latency_ms` — длительности стадий planner/generator/validator/reviewer;
- стабильность — совпадение исходов трёх сценариев в двух прогонах.

## Живой gate

Один прогон перед релизом на чистом SHA из `main`:

1. preflight: чистый worktree, версии runtime, digest модели, GPU;
2. шесть живых сценариев — требуется 6 из 6;
3. стабильность: три сценария по два прогона, исходы должны совпасть;
4. один прогон восьми слепых кейсов;
5. сборка компактного sanitized evidence.

Порог слепого набора — **не менее 7 из 8** проверенных кейсов, **ноль** `invalid_success_count` и **все** кейсы безопасности пройдены. Одна содержательная ошибка допустима: это честная оценка локальной модели, а не обещание непогрешимости. Опубликованный опасный кандидат недопустим ни при каком счёте.

Общий бюджет живого gate — **15 минут**; превышение само по себе является отказом гейта, чтобы проверка не разрослась обратно незаметно. По результатам слепого набора реализация не тюнится: найденные ошибки регистрируются для следующей версии.

## Release evidence

`scripts/release_gate.py --mode competition` работает только на чистой ревизии из `main` и требует внешний holdout. JSON-отчёт содержит:

- точный commit SHA и признак чистого worktree;
- SHA-256 корпуса и integrity report;
- версии Python, Lua, `luac`, Ollama и digest выбранной модели;
- GPU и доступную память;
- агрегаты по каждому этапу, длительность живого gate и коды отказов;
- для слепого набора — только имя, SHA-256, число кейсов, агрегированные метрики и категории ошибок, без пути к файлу и покейсных идентификаторов.

Успешный runtime snapshot получает `locked: true` только после всех проверок.

## Воспроизведение

При запущенной Ollama и установленной модели:

```bash
.venv/bin/localscript benchmark --dataset evals/live/v1.jsonl
.venv/bin/python scripts/bench_stability.py
```

Полный gate дополнительно требует владельца слепого набора и подходящую GPU-машину.

## Интерпретация

Корректная формулировка: «ревизия X прошла N/N живых сценариев и M/8 слепых кейсов в окружении Z; невалидных успешных исходов не обнаружено». Некорректная формулировка: «система гарантированно решает любые Lua-задачи».
