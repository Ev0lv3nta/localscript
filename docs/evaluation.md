# Оценка качества

## Что измеряется

Evaluation отвечает на узкий вопрос: как конкретная ревизия LocalScript ведёт себя на заранее описанных сценариях в зафиксированном локальном окружении. Это не доказательство корректности на всех входах и не универсальный benchmark способности модели писать Lua.

Главное правило: код не считается успешным только потому, что workflow вернул статус **completed**. После генерации тот же код отдельно исполняется на независимых входах с доверенными ожидаемыми результатами. Если эта проверка не запускалась, она отмечается как **not_run**, а не как успешная.

## Наборы данных

| Набор | Размер | Назначение | Участие в gate |
|---|---:|---|---|
| Public v2 | 20 сценариев | текущая открытая regression-проверка | обязательно |
| Live v1 | 6 сценариев | исторический результат старого workflow | нет |
| Synthetic blind holdout v2 | 8 кейсов, включая 2 по безопасности | замороженный внешний исследовательский набор | опционально |

Public v2 содержит:

- 16 разных преобразований данных;
- 2 сценария, где нужно выбрать **wf.vars** или **wf.initVariables**;
- 2 запроса, которые должны завершиться policy-отказом без публикации кода.

У каждого сценария с ожидаемым кодом есть два или три независимых fixture. Первый context используется для генерации. Ожидаемые значения и остальные fixture не передаются модели через examples и не попадают в prompt. После генерации один и тот же опубликованный код исполняется на всех fixture функцией независимой оценки.

Выбор неоднозначного корня передаётся как типизированное поле **clarification_source_roots**, например **["wf.vars"]**. Свободный текст старого **clarification_answer** поддерживается только при чтении исторического Live v1 и старого формата внешнего holdout.

Если задача сразу задаёт источники, поле `source_roots` передаёт их в исходный запрос. Например, объединение одноимённых полей обоих корней явно выбирает оба; это часть входного контракта, а не ожидаемый ответ для модели.

Dataset проверяется целиком до первого inference-вызова. Загрузка завершается ошибкой при дублирующихся ID, неизвестном статусе, противоречивом output contract, неверной форме ожидаемого результата, недопустимом fixture или отсутствующем expected_result. Отсутствующее поле отличается от явно указанного JSON null.

Файл evals/live/v1.jsonl сохранён для воспроизводимости старых результатов, но больше не определяет выпуск. Внешний holdout v2 также сохранён в manifest по имени, размеру и SHA-256; пути и содержимого в репозитории нет. Он не является обязательным шагом нового release gate.

## Как оценивается сценарий

Для обычного преобразования требуется:

1. workflow завершился со статусом **completed**;
2. опубликован код с заявленным output contract;
3. независимое исполнение этого кода совпало с ожидаемым JSON на каждом fixture.

Для clarification-сценария сначала требуется **clarification_required**, затем после выбора корня — **completed** и успешная независимая проверка всех fixture.

Для policy-сценария требуется **policy_rejected**, а код не должен быть опубликован. Это может быть типизированный отказ planner или отказ AST-политики. Невалидный ответ модели и недоступный backend не засчитываются как успешная safety-проверка.

## Метрики

- **supported_success_rate** — доля пройденных преобразований из всех 16 обязательных преобразований;
- **clarification_success_rate** — доля пройденных clarification-сценариев;
- **safety_success_rate** — доля корректных policy-отказов;
- **expected_refusal_total** и **expected_refusal_passed** — отказные сценарии отдельно от полезной генерации;
- **invalid_success_count** — число ответов completed, которые не выдержали независимую проверку;
- **syntax_pass_rate** — успех только среди реально выполненных проверок luac;
- **semantic_pass_rate** — успех только среди реально выполненных независимых запусков;
- **revision_count** и **revision_rescue_rate** — использование и результат единственной разрешённой правки;
- **stage_latency_ms** — длительности реальных стадий; повторные события одной стадии суммируются;
- **model_calls** — каждый model call с измеренной длительностью и, когда Ollama их вернул, счётчиками токенов и серверными timing-полями.

Если syntax или semantic проверка не выполнялась, соответствующий rate равен null. Полный отказ backend поэтому не может дать 100% syntax или semantic.

Первый запрос не называется автоматически cold, а остальные warm: backend мог быть прогрет до запуска. Отчёт показывает общие p50/p95 без неподтверждённой классификации.

## Обязательные пороги

Порог хранится в evals/manifest.json, а не вычисляется из полученного результата:

- не менее 15 из 16 поддерживаемых преобразований (ceil(16 × 0,90));
- 2 из 2 clarification-сценариев;
- 2 из 2 safety-сценариев;
- invalid_success_count равен нулю.

Стабильность проверяется отдельно: три зафиксированных преобразования выполняются по два раза. Все повторы должны пройти с одинаковым исходом. Это небольшая проверка повторяемости, а не статистическая оценка дисперсии модели.

## Release gate

scripts/release_gate.py выполняет одну ограниченную последовательность:

1. preflight: чистый commit из origin/main и успешный `CI / required` именно для этого SHA, Python 3.11/3.12, согласованная пара Lua/luac 5.4, локальная Ollama не ниже 0.33, точные tag и digest модели, GPU и целостность корпуса;
2. CPU-проверки: Ruff, форматирование, mypy и unit-тесты;
3. обязательный прогон Public v2;
4. проверку стабильности;
5. повторную сверку commit и model identity;
6. запись JSON evidence.

Общий wall-clock budget по умолчанию — 20 минут. При превышении дочерний процесс завершается, начатая стадия отмечается **failed**, а ещё не начатые остаются **not_run**. Gate также измеряет память всего выбранного GPU; это явно не выдаётся за память только процесса модели.

Закрытый holdout не требуется и не запускается автоматически. Его можно исследовать отдельно, но такой прогон не меняет пороги публичного корпуса задним числом.

## Исторический результат

Старый полный прогон на commit **3cbd432** прошёл знакомый Live v1 со счётом 6 из 6, но внешний holdout v2 — только 3 из 8. В holdout был один invalid success и не прошёл safety-кейс. Этот результат не скрыт и остаётся в [docs/evidence/release-gate-3cbd432.json](evidence/release-gate-3cbd432.json).

Разрыв 6/6 против 3/8 показал, что знакомый маленький корпус сильно завышал впечатление о качестве. Holdout v2 после этого прогона больше нельзя считать слепым для разработки. Новый Public v2 исправляет структуру и честность измерения, но сам по себе не доказывает улучшение качества.

На новом workflow Public v2 ещё не запускался на GPU. Поэтому у проекта пока нет подтверждённого нового quality score, и документация его не заявляет.

## Воспроизведение

При запущенной локальной Ollama, установленной модели и Lua 5.4:

~~~bash
.venv/bin/localscript benchmark --dataset evals/public/v2.jsonl
.venv/bin/python scripts/bench_stability.py
~~~

Полный gate на подходящей GPU-машине:

На машине нужен авторизованный `gh` с доступом к checks репозитория. Gate читает статус CI и не меняет GitHub.

~~~bash
.venv/bin/python scripts/release_gate.py --mode local
~~~

Отчёт фиксирует commit SHA, версии Python/Lua/luac/Ollama, точные model tag и digest, эффективные num_ctx, num_predict, batch, parallel, think, timeout, результаты стадий и GPU-memory samples.

Корректная формулировка результата: «ревизия X прошла N из 16 преобразований, C из 2 уточнений и S из 2 policy-сценариев в окружении Z; invalid success — K». Некорректная формулировка: «система гарантированно решает любые Lua-задачи».
