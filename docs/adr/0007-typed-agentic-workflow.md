# ADR 0007: typed agentic workflow вместо family-router

- Статус: принято
- Дата: 13 августа 2026 года
- Заменяет: [ADR 0002](0002-resolved-task-and-generation-stages.md), [ADR 0003](0003-family-registry.md), [ADR 0006](0006-repair-boundaries.md)

## Контекст

Генерация опиралась на `TaskExtractor`, который классифицировал запрос регулярными выражениями и keyword-лестницами, на реестр из шестнадцати семейств задач и на канонические замены кода для узких случаев. Такая схема выдерживала известные формулировки, но новая композиция операций или перефразированный запрос требовали новой Python-ветки. Заявление об «агентной архитектуре» при этом было сильнее фактического устройства: решение принимал rule-based слой, а не модель.

Отдельная проблема — замкнутость проверки на реализацию. Deterministic oracle знал ожидаемую форму результата для своего семейства, поэтому eval проверял ту же таблицу, которая порождала код.

## Решение

Генерация становится ролевым workflow на одной локальной модели:

`planner → generator → deterministic validation → reviewer → не более одной revision`

- Естественный язык не классифицируется кодом. Детерминированным остаётся только `ContextInventory`: обход JSON-контекста, типы значений и пути.
- Planner возвращает `TaskPlan` либо `ClarificationRequest` — один discriminated union, проверяемый JSON Schema. План содержит цель, входные `WorkflowPath`, `OutputContract`, шаги, ограничения и от одного до трёх исполнимых acceptance cases.
- Generator возвращает `CodeCandidate` без markdown и пояснений.
- Проверка кандидата детерминирована: AST-policy, `luac`, выполнение в ограниченном runtime и сравнение результата acceptance cases по структуре JSON.
- Reviewer работает в свежем контексте, видит запрос, план, код и результаты проверки, но не внутренний вывод generator.
- При отказе validation или reviewer разрешена ровно одна полноценная revision через модель. Строковых переписываний кода и канонических шаблонов не остаётся.
- `WorkflowState` неизменяем и сам запрещает противоречивые сочетания стадии и артефактов, а `WorkflowResult` не может опубликовать `code` без успешной валидации.

Невалидный структурированный ответ модели получает одну schema-correction попытку; после неё операция завершается fail-closed.

## Последствия

Ожидаемая форма результата задаётся планом для конкретного запроса, а не таблицей семейств, поэтому перефразирование и новая композиция операций больше не требуют изменения Python-кода. Проверка перестаёт быть замкнутой на реализацию: acceptance cases приходят из плана и исполняются, а не сверяются с зарегистрированным oracle.

Цена — три обращения к модели на обычный запрос вместо одного и зависимость качества от способности локальной модели соблюдать JSON Schema. Reviewer работает на той же модели, что и generator, поэтому он ловит расхождение с планом, но не является независимой экспертизой; в README это названо прямо.

Удалено около девяти тысяч строк: `TaskExtractor`, `TaskResolver`, `app/families`, semantic oracles, canonical repair и привязанные к ним тесты. Тесты, проверявшие внутренние детали старого router, удалены вместе с ним, а не переписаны под новую реализацию.
